# ThinkRAG 代码覆盖率报告

> 采集时间：2026-10-20 14:14
> 采集方式：`pytest -m "not slow" --cov=server --cov=frontend`
> 用例数：33 passed / 12 xfailed（真实 bge-small 嵌入 + DeepSeek，非 Mock）

## 一、结论先看

| 口径 | 覆盖率 | 说明 |
|---|---|---|
| **全仓（server + frontend）** | **28%** | 1295 条语句覆盖 358 条 |
| **server 业务层** | **55%** | 651 条语句覆盖 358 条 |
| frontend 页面层 | 0% | 644 条语句，本套 pytest 未覆盖 |

**为什么有两个口径**：frontend 是 10 个 Streamlit 页面文件，全部语句都是 `st.xxx` 的界面代码，必须由 UI 驱动才能执行。本套 pytest 是业务层测试（直接调 `IndexManager`、`create_query_engine`），不启动 Streamlit 进程，所以这部分天然是 0%。

这不是"漏测"，而是**测试分层**：

| 层 | 覆盖手段 | 现状 |
|---|---|---|
| 页面交互层 | Playwright（`probe_ui.py` / `probe_final.py`） | 有 3 段脚本，未纳入本次覆盖率统计 |
| 业务逻辑层（server） | pytest | **55%** |
| 外部依赖 | 真实 DeepSeek / 本地 bge-small | 问答质量 11/11 命中 |

面试时应主动说清这个口径，不要报"整体 28%"——那是把 UI 代码也算进分母得出的数字，会让人误判测试深度。

## 三、这一轮提升做了什么

补充用例前 server 层是 **43%**，本轮新增 `tests/test_06_core.py` 6 条用例后提升到 **55%**（+12pp）。这 6 条不是为覆盖率凑数，都是之前矩阵漏掉的真实入口：

| 用例 | 覆盖的功能 | 为什么重要 |
|---|---|---|
| `test_load_dir_indexes_all_files` | `IndexManager.load_dir` | File 页除单文件上传外还有批量导入入口，之前只测了 `load_files` |
| `test_index_reload_after_restart` | `check_index_exists` + `load_index` | **BUG-TRAG-001 的同一条路径**，重启后读错索引就全崩 |
| `test_load_index_by_id` | `load_index` 按 id 载入分支 | 多索引场景下的正确载入方式 |
| `test_chinese_text_splitter_sentence_split` | 中文句子切分 | 中文文档切块质量直接影响召回 |
| `test_chinese_recursive_splitter_chunk_size` | 递归分块边界 | chunk_size 是硬约束，验证超长文本被正确截断 |
| `test_sanitize_metadata_for_json` | metadata 清洗 | Web 抓取的 bs4.Tag 混入会导致持久化失败 |

其中索引重载那条最值得讲：它把 BUG-TRAG-001 的成因（空索引被优先加载）变成了**每次回归都会检查的用例**，而不是靠人工偶然发现。

## 四、为什么没有追求更高

三个现实约束：

1. **frontend 644 行需要 UI 自动化才能覆盖**。Streamlit 的页面逻辑大量写在 `if st.button()` 分支里，Playwright 能点按钮，但要覆盖每个分支需要大量 UI 脚本，投入产出比低。更合理的做法是 UI 只测关键路径（提问、上传、删除三条），业务逻辑全放在 pytest。
2. **多存储后端是可选能力**。项目支持 Chroma / LanceDB / ElasticSearch / Redis，但 DEV_MODE 下默认用 SimpleVectorStore（本地 JSON）。为每个后端起一套环境属于集成测试范畴，超出"个人项目测试"的合理范围。
3. **LLM 厂商分支无密钥**。OpenAI / Ollama 需要额外账号或本地模型，只验证了 DeepSeek。

这三条都是**主动选择不测**，不是遗漏。面试被问到时直接说"我知道哪里没覆盖，为什么没覆盖"，比报一个漂亮数字可信得多。

## 六、面试口径（可直接念）

> 这套测试的覆盖率统计口径是业务层，server 目录 55%。仓库里还有 644 行是 Streamlit 页面代码，占整体一半多，必须由 UI 驱动才能跑到，所以整体数字是 28%——我不建议拿整体数字说事，那会把 UI 代码算进分母。
>
> 覆盖率提升最明显的一次是补了索引重载的用例，server 从 43% 到 55%。因为发现过一个 P1 缺陷：删空知识库再重新上传会留下空索引，重启后读到空索引，查询 100% 失败但界面只提示"答不出"。把这条路径固化成用例后，每次回归都会检查。
>
> 没覆盖的部分我也清楚：Web 抓取要联网、OpenAI/Ollama 没密钥、Chroma 这些后端默认不启用。这些属于主动不测，不是漏掉。
